# Dialect courses: mechanism, codes and candidates (2026-11-23)

Answers MASTER-PLAN §0.5 ("give each dialect its own course"). First course: **Dominican Spanish for English speakers** (`en-esdo`), learner profile `docs/profiles/en-esdo.md`. Nothing here is built yet. Numbers marked *measured* come from a script run against `tools/target/es/` on 2026-11-23; everything else is an estimate.

## 0. Decisions proposed

1. A dialect course is built by a **dialect layer** over an existing course (the base), not by copying the base folder. The output is a normal course folder, so `gen.js`, `validate.js` and `repron.js` run unchanged.
2. Exception: when the two varieties share less than about 60% of their cards, write a separate course (as was done for Portugal Portuguese).
3. Code for Dominican Spanish: **`esdo`**, course id `en-esdo`. The existing `es` course keeps its code and becomes **"Spanish (Mexico)"** with a Mexican flag. Nobody loses progress.
4. Progress does **not** sync between dialect courses. Instead, the first time a learner opens a sister dialect course, the app offers a **one-time import** of the cards and lessons the two courses share.

## 1. How a dialect course is produced

### 1.1 Copy or layer?

What the Portuguese split shows (*measured*): `ptpt` shares only **33 of its 300 card targets** and **13 of its 28 lesson ids** with `pt`. That split was really a new course written from the same template, so copying the folder cost little: almost every row was rewritten anyway.

Spanish (Mexico) and Spanish (Dominican Republic) are much closer. The Dominican plan in `en-esdo.md` keeps **851 of the 925 base cards unchanged (92%)**, gives 22 cards a new target and 35 cards only a new note, drops one card and the 16-card Caribbean deck, and adds 98 Dominican cards (*measured* against the planned override list). In the examples, 12 of 111 dialogue rows, 13 of 253 example rows and 2 of 27 patterns need a change.

| | Copy the folder (as `ptpt`) | Dialect layer (recommended for Spanish) |
|---|---|---|
| Work to start | Lowest: `cp -r`, then edit | A build step to write once (`dialect.js`, about 300 lines) |
| Duplicated text | All of it: about 1,000 cards, 26 lessons, 360 practice items twice | Only the rows that differ (about 8% of cards, 3 to 6 lessons' worth of passages) |
| A fix in the base (e.g. a wrong `why` in `gustar`) | Must be made by hand in every copy, and nobody notices when a copy is missed | Reaches every dialect at the next build |
| A base edit that touches an overridden row | Silent | The build fails and names the row (§1.4), so a person decides |
| Reviewing a dialect | Reviewer must read the whole course to find the dialect | Reviewer reads the layer: every dialect decision is in one place |
| Risk | Copies drift apart | A bad override can break a practice item's grammar (gender swaps); caught by `validate.js` and the forbidden-term scan |
| Right when | Less than ~60% of cards shared (Portugal, Arabic dialects vs MSA) | More than ~60% shared (Spanish varieties, US/UK English, France/Québec French) |

**Recommendation: layer** for every Spanish dialect and for the other close pairs in §3; copy only where §3 says "separate course".

### 1.2 On-disk format

Sources live in **`tools/dialects/<code>/`**. The build writes a complete, ordinary course into **`tools/target/<code>/`**, which carries a `GENERATED` file and a header comment in every file ("generated by tools/target/dialect.js from tools/dialects/esdo and tools/target/es: edit those"). This keeps `tools/target/<t>/` meaning "a course gen.js can read", and keeps hand-written and generated files apart.

```
tools/dialects/esdo/
  base.json            which course it layers, profile changes, lesson and deck lists, drops, forbidden terms
  overrides-cards.js   changed cards, keyed by deck + base target
  overrides-extra.js   changed DIALOG / EXAMPLES / PATTERNS rows, keyed by base key
  overrides-lessons.js changed lesson text and practice items, keyed by lesson id
  decks-do.js          dialect-only decks      (normal en-<t> writer format, TARGET-BRIEF)
  extra-do.js          dialect-only DIALOG / EXAMPLES / PATTERNS
  lessons-do.js        dialect-only lessons
  respell.js           the dialect's pron generator (may require the base generator)
  REVIEW.md            review notes, as in other course folders
```

**`base.json`**

```json
{
  "base": "es",
  "profile": { "target": "esdo", "nameEn": "Spanish (Dominican)", "self": "Español dominicano",
               "ttsLang": "es-DO", "brand": "Dominicano",
               "greet": [["Buenas noches","Good night (you're up late)"],["Buenos días","Good morning"],["Buenas tardes","Good afternoon"],["Buenas noches","Good evening"]] },
  "lessons": ["sounds", "do-sounds", "greetings", "do-greetings", "gender", "…full order, base ids and new ids…"],
  "decks":   ["Sounds and spelling", "…every base deck kept…", "Dominican sounds", "…new decks…"],
  "dropLessons": ["caribbean"],
  "dropDecks": ["Caribbean and Dominican Spanish"],
  "forbid": ["\\btacos?\\b", "tortilla", "quesadilla", "tamal", "taquer", "Canc[uú]n", "Puebla", "Monterrey", "Guadalajara", "Oaxaca",
             "cami[oó]n", "jamaica", "Lupita", "[¡]?[OÓ]rale", "H[ií]jole", "[¡]Aguas", "\\bcuate\\b", "gripa"],
  "forbidAllowIn": ["deck:Mexico or the DR? Word traps", "note"]
}
```

- `lessons` and `decks` are the **full ordered lists** of the dialect course. A base lesson or deck missing from both the list and the drop list is a build error, so a lesson added to the base later is never silently inherited or lost.
- The profile's lesson and deck entries (`title`, `roadmap`, `deck`, `group`, `desc`) come from the base profile for inherited ids and from `decks-do.js` / `lessons-do.js` headers for new ones; `base.json` may override any field by id.
- `forbid`: regular expressions that must not appear in any target, example, dialogue, lesson body or practice item of the built course. Card notes (where "Mexico: los frijoles" is the point) and the named traps deck are allowed. This catches Mexican content the layer forgot, including content added to the base later.

**`overrides-cards.js`** (one row per changed card, `pron` never written: it is always regenerated)

```js
module.exports = {
  "Food and drink": `
    los frijoles | las habichuelas | beans | Mexico: los frijoles. Feminine: las habichuelas rojas.
    unos tamales | unos pasteles en hoja | Dominican tamales | Plantain or yuca dough with meat, wrapped in a banana leaf.
    el desayuno |  |  | Many Dominicans eat mangú for breakfast.
  `,
  "Top adverbs": `
    ahorita |  | in a while; later | In the DR ahorita means later, not now. Right now: ahora mismo.
  `
};
```

Fields: `base target | new target | new meaning | new note`. An empty field keeps the base value. A new target of `-` drops the card. A changed target **re-keys** the card, so every DIALOG and EXAMPLES row keyed by the old target must be replaced in `overrides-extra.js`, or the build fails. Rows are never changed by string substitution: *el autobús → la guagua* changes gender, so every article, adjective and `why` around it must be rewritten by a person.

**`overrides-extra.js`**

```js
exports.DIALOG = `
  unos tamales | unos pasteles en hoja | ¿Hay pasteles en hoja hoy? | Sí, de pollo y de cerdo. | Are there pasteles today? / Yes, chicken and pork.
`;
exports.EXAMPLES = `
  Voy a viajar a Cancún. | Voy a viajar a Punta Cana. | Voy a viajar a Punta Cana en diciembre. | I'm going to travel to Punta Cana in December.
`;
exports.PATTERNS = `
  <base row, exactly as in the base, 4 fields> => <new row, 4 fields>
`;
```

The first field is the base key; it must exist. A row with a new key but no base key adds a row; `base key | -` removes one.

**`overrides-lessons.js`**

```js
module.exports = {
  gustar: {
    body: [
      ["{{ex:Me gustan los tacos.|", "{{ex:Me gustan los tostones.|"],
      ["{{ex:Me encantan los tamales.|", "{{ex:Me encantan las habichuelas con dulce.|"]
    ],
    practice: {   /* positions count from 0; these are the real base rows */
      5: { was: ["or","I like tacos.","Me gustan los tacos","gusta","Gustan agrees with los tacos, which is plural."],
           row: ["or","I like tostones.","Me gustan los tostones","gusta","Gustan agrees with los tostones, which is plural."] },
      8: { was: ["fi","Me __ las quesadillas.","I like quesadillas.","gustan","gusta|gusto|gustas","Las quesadillas is plural, so gustan."],
           row: ["fi","Me __ las habichuelas.","I like beans.","gustan","gusta|gusto|gustas","Las habichuelas is plural, so gustan."] }
    },
  },
  questions: { body: [["<div class=\"tip\">", "<h3>¿Qué tú quieres?</h3><p>…</p><div class=\"tip\">"]] }
};
```

- `body`: `[old, new]` pairs. Each `old` must occur **exactly once** in the base body (the same rule as the Artifact tool's `edits`). A pair that matches zero or two places fails the build.
- `practice` and `check`: keyed by the item's position, and each carries `was`, the exact base row it replaces. If the base row changed, the build fails ("base edited `gustar` practice 4 since this override was written").
- `title`, `blurb`: plain replacement.
- Example rows inside a body keep their `{{ex:target|pron|English}}` shape; the pron written there is ignored and regenerated.

### 1.3 The build step: `tools/target/dialect.js`

```
node tools/target/dialect.js esdo            # writes tools/target/esdo/
node tools/target/dialect.js esdo --check    # no writing: reports drift and exits 1 on any problem
node tools/target/gen.js esdo && node tools/target/validate.js esdo
```

Steps:
1. Load the base with `LIB.load(base)` and its `profile.json`.
2. Check the lesson and deck lists against the base (every base id is kept or dropped explicitly).
3. Apply drops, then card overrides (re-keying DIALOG and EXAMPLES), extra overrides, lesson overrides. Every `was` and every `old` must match.
4. Add the dialect-only decks, extras and lessons.
5. **Regenerate every pron** (cards and `{{ex:}}` rows) with `tools/dialects/<code>/respell.js`, using the same logic as `tools/target/repron.js`. Prons are never inherited and never hand-written: the Dominican pron differs from the Mexican one in about half of all strings (every coda *s*), so inheriting them would be wrong.
6. Scan for `forbid` terms (§1.2).
7. Write `tools/target/<code>/` as ordinary files (`profile.json`, `decks-*.js`, `extra-*.js`, `lessons-*.js`, `respell.js`), plus `BASE.json` recording the base files' SHA-1 hashes and the counts (cards inherited / overridden / added, items overridden).

`validate.js` then checks the result exactly as for any course: deck sizes (12+ cards), unique meanings per deck, the standing rule in every lesson, the practice mix, pron pattern, one pron per string. A layer that swaps *el autobús* for *la guagua* in a practice item but leaves *el* in the tiles fails here only if the `why` or distractor logic breaks; the person writing the override owns the grammar.

### 1.4 Keeping in step with the base

- `build.sh` runs `dialect.js <code> --check` for every dialect before packing. It fails when:
  1. an override's `was` / `old` no longer matches (the base edited a row the dialect also changed: a person merges);
  2. a `forbid` term appears (the base added, say, a *tacos* sentence: add an override);
  3. the base added or removed a lesson or deck that `base.json` does not list.
- Anything else the base changes (a fixed `why`, a better example, a new card) reaches the dialect automatically at the next build. `BASE.json` lets the report say what came in ("base changed since last build: 14 rows inherited, 0 conflicts").
- A base course under `HOLD` holds its dialects too.
- Reviews: a cold review of the base counts for the inherited 92%; a dialect review covers the layer files plus a read-through of the built lessons that carry overrides.

## 2. Codes, names, flags, voices, progress

### 2.1 Codes and names

- **Code pattern:** the base code plus the ISO 3166 country code in lower case (`esdo`, `esar`, `frca`, `engb`), or an ISO 639-3 code where one exists for a dialect that is a separate course (`arz` Egyptian, `apc` Levantine, `ary` Moroccan). Both fit the course id pattern `^[a-z]{2,3}-[a-z]{2,4}$` in `validCourse` and `^[a-z]{2,4}$` in `tools/target/lib.js`.
- **Dominican Spanish:** code `esdo`, course id `en-esdo`.

| | `es` (existing) | `esdo` (new) |
|---|---|---|
| `nameEn` (picker, English) | Spanish (Mexico) (today "Spanish (Latin American)") | Spanish (Dominican) |
| `self` | Español (México) | Español dominicano |
| Korean label (`LANGS.ko`) | 스페인어 (멕시코) | 스페인어 (도미니카) |
| Flag in "language to learn" | 🇲🇽 | 🇩🇴 |
| `ttsLang` | es-MX (unchanged) | es-DO |
| `voiceMatch` | none | **none** (see §2.2) |
| HTML `lang` (`hLang`) | es | es-DO |

**Renaming `es`:** change only `nameEn`, `self` and the target flag. Keep the code `es` and the course id `en-es`: progress is stored under `la-s-en-es` (`stateKey`), lesson progress under lesson ids and card progress under `deck|target` (`ck`), so a code change would orphan every Spanish learner's progress. A name change touches nothing saved.

**Engine items for the lead** (not done here; other agents own `src/app.html`):
1. Add `esdo` to `LANGS` with `t:1` (as `ptpt`): `validCourse` rejects a course whose target is not in `LANGS`.
2. `hLang`: `esdo` → `es-DO`.
3. **A target flag separate from the interface-language flag.** `LANGS.es.flag` (🇪🇸 today) is also the flag of Spanish as the learner's own language in step 1, where a Mexican flag would be wrong for a speaker from Spain. Add an optional `tflag` (flag in "language to learn") to `LANGS` entries, used by the step-2 picker and the course button: `es` → 🇲🇽, `esdo` → 🇩🇴, `pt` → 🇧🇷, `ptpt` → 🇵🇹. Step 1 keeps one entry per language.
4. The picker should show sister dialect courses next to each other (sort by base language, then by `nameEn`).
5. `audio/esdo/f/` and `audio/esdo/m/`: clips are fetched from `audio/<target>/`, so the Dominican course gets its own recordings and never plays the Mexican ones.
6. `tools/audio/voices.json`: an `esdo` entry (Azure and ElevenLabs).

### 2.2 Voices

- **Azure:** a third-party voice catalogue lists two Spanish (Dominican Republic) Azure voices, `es-DO-RamonaNeural` (woman) and `es-DO-EmilioNeural` (man) ([json2video, Dominican Republic](https://json2video.com/ai-voices/languages/spanish/dominican-republic/); [Emilio](https://json2video.com/ai-voices/azure/voices/es-do-emilioneural/)). Microsoft's own language-support page, as fetched, showed `es-DO` only in the speech-to-text table; the TTS table was cut off. Confirm with `gen_azure.js --dry` or the voices REST list before relying on it. Whether these voices weaken *s* or velarise *n* is not known: listen before choosing (the test script in `en-esdo.md` §11).
- **ElevenLabs:** voices belong to speakers, not locales. Ask for (or search the voice library for): a native Dominican speaker from Santo Domingo, one woman and one man, 25 to 45, educated everyday speech, warm and unhurried, who **aspirates syllable-final s and says final n as ng in conversation but does not lateralise r to l or drop whole syllables**. Test with the same 10-sentence script, on the model in `voices.json` (`eleven_v4` for Korean) and on `eleven_multilingual_v2`: a multilingual model can pull an accent toward a neutral or Mexican Spanish.
- **Device voice fallback:** phones rarely carry an `es-DO` voice. With no `voiceMatch`, `pickVoice` takes an exact `es-DO` voice if there is one, else any `es-*` voice. That keeps the course audible offline. The cost: a Mexican or Spain device voice contradicts the Dominican pron line, which is why the profile switches the pron line to Dominican-natural only once recorded clips cover the course (`en-esdo.md` §6).

### 2.3 Saved progress

- **Renaming / relabelling `es`:** no effect on saved progress (above).
- **Splitting:** existing `en-es` learners stay in `en-es`; nothing moves. A learner who wanted Dominican Spanish opens `en-esdo` as a new course.
- **Should progress carry between dialect courses? Recommendation: a one-time, opt-in import; no live sync.**
  - Card progress is keyed `deck|target`. Because the layer keeps deck names and 92% of targets, `S.cards` entries from `la-s-en-es` can be copied to `la-s-en-esdo` where the same key exists in the new course; lesson completion copies for inherited lesson ids (25 of 31 in `en-esdo`).
  - Offer it once, when `en-esdo` is opened for the first time and `la-s-en-es` exists: "You know 240 cards and 11 lessons from Spanish (Mexico). Start Spanish (Dominican) with them?" Yes copies; no starts fresh.
  - Why not live sync: the two courses teach different words for the same card slot (*autobús / guagua*) and different prons, and a learner who studies both would see one course's review schedule move because of the other. Copying once gives the shortcut without the confusion.
  - Engine work: about 40 lines in `src/app.html` (lead).
